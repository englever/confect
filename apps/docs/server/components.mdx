Convex [components](https://docs.convex.dev/components) are configured in `convex/convex.config.ts`. Unless your backend has a [backend declaration](/server/backend-declaration), Confect does not manage that file, and you configure components with the vanilla Convex API. With a declaration, you mount components with `App.mount` in `confect/app.ts`, and `confect codegen` writes `convex/convex.config.ts` for you.

```ts convex/convex.config.ts
import { defineApp } from "convex/server";
import workpool from "@convex-dev/workpool/convex.config";

const app = defineApp();
app.use(workpool, { name: "workpool" });

export default app;
```

## Referencing components

Component clients (like `Workpool`) take a component reference. Import the typed `components` registry that Confect generates at `confect/_generated/components.ts`:

```ts confect/workpool.ts
import { Workpool } from "@convex-dev/workpool";
import { components } from "./_generated/components";

const pool = new Workpool(components.workpool, {
  maxParallelism: 3,
});
```

<Note>
  Use this registry rather than the `components` export of
  `convex/_generated/api`, which doesn't exist yet when `confect codegen`
  evaluates your code and so breaks codegen on a clean checkout. Confect's
  registry is equivalent, but is derived directly from
  `convex/convex.config.ts`, so it is safe to import anywhere in your `confect/`
  directory.
</Note>

<Note>
  Each component is typed with the `ComponentApi` type that component packages
  export from `_generated/component.js`. Recently published versions of the
  official `@convex-dev/*` components all follow this convention; a component
  that predates it will still work at runtime but won't get precise types.
</Note>

## Defining functions for components

Some components (such as [Workflow](https://www.convex.dev/components/workflow), [Migrations](https://www.convex.dev/components/migrations), and [Workpool](https://www.convex.dev/components/workpool)) expect you to define Convex functions in your project that they can reference. You can integrate these into your Confect spec and impl using [plain Convex functions](/server/plain-convex-functions).

See the [Convex components documentation](https://docs.convex.dev/components) for details on installing and using components.

## Use a published Confect component

A Confect component is a normal Convex component with an additional contract containing its public function codecs. Install its Convex definition with `app.use`, then bind the contract to the generated registry entry:

```ts confect/counter.ts
import { Component } from "@confect/core";
import contract from "@example/counter/confect";
import { components } from "./_generated/components";

export const counter = Component.bind(contract, components.counter);
```

Call bound references with `QueryRunner`, `MutationRunner`, `ActionRunner`, or `Scheduler`, just like your application's references. Arguments and returns use the component's decoded Effect types; declared errors enter the Effect error channel. Bound references are backend-only: expose your own application functions for frontend access.

```ts
import * as Effect from "effect/Effect";
import { MutationRunner } from "./_generated/services";
import { counter } from "./counter";

const create = Effect.gen(function* () {
  const mutation = yield* MutationRunner;
  return yield* mutation.runMutation(counter.counter.create, { count: 3 });
});
```

The extra `counter` segment in this example is the component's `counter.spec.ts` function group. Binding preserves the component's exported group structure.

### Store component IDs in application tables

Each installation has its own ID type. An application ID, a component ID, and an ID from a second installation are different types even when their table names match.

```ts confect/tables/links.ts
import { Component, Table } from "@confect/core";
import * as Schema from "effect/Schema";
import { counter } from "../counter";

export default Table.make(() =>
  Schema.Struct({ counterId: Component.id(counter, "counters") }),
);
```

`Component.id` also supports `_storage` and `_scheduled_functions` for generated contracts. Use `Component.schema(counter, exportedCodec)` to rebind IDs inside a codec exported by the component, including nested objects and arrays.

Scopes change TypeScript identity and validator selection, not ID strings. At four mount levels, such as `left/deep/child/child`, installations can lose compile-time ID separation. IDs owned by the current database compile to `v.id(tableName)`; IDs from another database compile to `v.string()`. A foreign ID field therefore does not validate ownership at runtime. Validate untrusted references through the owning component and perform authorization in your application.

<Warning>
  Keep the generated registry's literal mount names. Widening a component API to
  `any` or an unspecified mount name loses compile-time instance separation.
  Scopes are not an authorization mechanism.
</Warning>

### Wrap a vanilla component reference

For a component without a Confect contract, `Ref.fromFunctionReference` adapts a native function reference for Confect's runners and scheduler. Its types and values remain the native wire types; it does not add codecs, scoped IDs, or declared Effect errors.

```ts
import { Ref } from "@confect/core";
import { components } from "./_generated/components";

const create = Ref.fromFunctionReference(components.counter.counter.create);
```

## Author a component

Use the same table, spec, and implementation APIs as an application. Put `confect/` next to the component's Convex directory, inside a package with a `name` in `package.json`:

```text
package.json
src/
  confect/
    tables/counters.ts
    counter.spec.ts
    counter.impl.ts
  convex/
    convex.config.ts
```

```ts src/convex/convex.config.ts
import { defineComponent } from "convex/server";

export default defineComponent("counter");
```

Run Confect codegen before Convex's component codegen:

```sh
confect codegen --component-dir src/convex
convex codegen --component-dir src/convex
```

For watch mode, use `confect dev --component-dir src/convex` alongside your Convex development workflow. These commands target one component; run application codegen separately.

Confect generates the usual IDs, tables, schema, services, references, and registered functions, plus `confect/_generated/component.ts`. That file exports the publishable contract. Only public functions appear in the contract's bound reference tree; internal functions remain callable inside the component through its own generated references.

The generated definition scope derives from the nearest package's name and the component directory's package-relative path. Keep that identity stable and import `Id` from `_generated/id` when declaring the component's own IDs. Existing application IDs remain compatible with Convex's `GenericId` type.

Scope parameters accept the branded `IdScope.IdScope` type, not raw strings. Prefer the generated `scope` from `_generated/id`. For hand-authored schemas, import `IdScope` from `@confect/core` and use `IdScope.app`, `IdScope.component(name)`, or `IdScope.instance(parentScope, name)`. These helpers preserve scope identity in the types without changing the runtime strings or checking ownership.

### Handler capabilities

Keep using `FunctionImpl.make(databaseSchema, group, name, handler)` with the generated schema. The schema determines the available services:

- Database operations address the component's database, with scoped document IDs.
- `StorageReader`, `StorageWriter`, `StorageActionWriter`, and `Scheduler` use IDs in that same component scope. The unified `Storage` service is application-only.
- Generated raw contexts preserve scoped ID types and omit `auth`.
- Application `Auth` is unavailable. Pass the identity information your component needs explicitly in function arguments.

The component `Scheduler` interface supports `runAfter` and `runAt`. It does not yet expose `cancel`.

Convex rejects `"use node"` inside components. Keep Node actions in the host application.

Component codegen rejects `confect/auth.ts`. Configuration reads still use Convex's environment provider; declare component environment variables through the native component configuration API.

For Effect HTTP routes, use `HttpRouter.forSchema(databaseSchema)(routes)` so route capabilities follow the component schema too. Mount the component's routes using Convex's component HTTP routing API. The schema-free `HttpRouter.make(routes)` remains the application API.

Convex's built-in database pagination is not supported inside components. Use [stream queries](/server/database/streams) for component pagination instead of the native `.paginate()` path. Plain Convex functions retain their native contexts and runtime restrictions; Confect does not rewrite their handlers.

### Install a child component

Use `defineComponent(...).use(...)` in the component configuration. Bind the child's contract with the enclosing component's generated scope:

```ts src/confect/child.ts
import { Component } from "@confect/core";
import childContract from "@example/child/confect";
import { components } from "./_generated/components";
import { scope } from "./_generated/id";

export const child = Component.bind(childContract, components.child, {
  parentScope: scope,
});
```

The `parentScope` keeps child IDs associated with the enclosing installation when a parent contract returns them. Omit it when binding in the root application.

## Call back into the host

A component sometimes needs to call a function its host owns: an email component reports that a message bounced, a job queue reports that a job finished. The component declares a callback contract, the host creates a handle for one of its functions, and the component stores the handle and runs it later.

### Declare a contract

Declare contracts in the component with `Callback.mutation`, `Callback.query`, or `Callback.action`. The id has the form `"<component>/<event>"`. `args`, `returns`, and `error` are thunks, as in `FunctionSpec`, so declaring a contract builds no schema. Name a declared error for the fact it reports.

```ts src/confect/callbacks.ts
import { Callback } from "@confect/core";
import * as Schema from "effect/Schema";

export class EventRejected extends Schema.TaggedError<EventRejected>()(
  "EventRejected",
  { reason: Schema.String },
) {}

export const Status = Schema.Literals(["queued", "sent", "bounced"]);

export const OnEvent = Callback.mutation("email/onEvent", {
  args: () => ({ emailId: Schema.String, status: Status }),
  returns: () => Schema.Null,
  error: () => EventRejected,
});
```

The module imports nothing from `@confect/server`, so a host can import the contract and its errors when it implements the callback.

### Store and run a handle

`Callback.handle(OnEvent)` is the schema of a handle. On the wire and in the database it is a string (`v.string()`); in handlers it is a reference that `MutationRunner`, `QueryRunner`, `ActionRunner`, and `Scheduler` accept. Use it in function args and table fields:

```ts src/confect/tables/emails.ts
import { Callback, Table } from "@confect/core";
import * as Schema from "effect/Schema";
import { OnEvent, Status } from "../callbacks";

export default Table.make(() =>
  Schema.Struct({
    to: Schema.String,
    status: Status,
    onEvent: Callback.handle(OnEvent),
  }),
);
```

Run the stored handle like any other reference. Args are encoded and returns decoded with the contract's codecs, and the contract's declared errors arrive in the Effect error channel:

```ts
const notify = (id: Id<"emails">) =>
  Effect.gen(function* () {
    const reader = yield* DatabaseReader;
    const runner = yield* MutationRunner;
    const scheduler = yield* Scheduler;
    const email = yield* reader.table("emails").get(id);

    yield* runner
      .runMutation(email.onEvent, { emailId: id, status: "bounced" })
      .pipe(
        Effect.catchTag("EventRejected", (rejected) =>
          Effect.log(rejected.reason),
        ),
      );

    yield* scheduler.runAfter(Duration.zero, email.onEvent, {
      emailId: id,
      status: "sent",
    });
  });
```

A handle accepts only the args its contract declares, and a handle made for one contract is not assignable to a field typed with another, even when the shapes match.

### Create a handle in the host

The host creates a handle with `Callback.create` from `@confect/server` and passes it as an ordinary argument:

```ts confect/emails.impl.ts
import { Callback } from "@confect/server";
import { OnEvent } from "@example/email/callbacks";
import refs from "./_generated/refs";
import { MutationRunner } from "./_generated/services";
import { email } from "./email";

const send = Effect.gen(function* () {
  const onEvent = yield* Callback.create(OnEvent, refs.internal.emails.onEvent);
  const runner = yield* MutationRunner;
  return yield* runner.runMutation(email.email.send, { to, onEvent });
});
```

`Callback.create` checks the reference against the contract twice: its types at compile time, and the validators Convex compiles for both when the host creates the handle. The validator check is the guarantee. The type check catches the common mistakes where you write the call.

At compile time it compares the types that cross the wire:

- The function type: a query cannot stand in for a mutation contract.
- Args and returns: the host's encoded args and returns must equal the contract's, with a component's IDs compared as strings. Convex's validator rejects any field the host does not declare, so a host that accepts wider args is refused too. A host that returns `Schema.Finite` (a number on the wire) does not satisfy a contract that returns `Schema.FiniteFromString` (a string on the wire), even though both decode to `number`. Reuse the contract's schemas, which the component exports with the contract.
- Errors: the host must not fail with errors the contract does not declare, and its errors, including those of its middleware, must decode with the contract's codecs.

When a check fails, the compiler error names the first mismatch, for example `the ref's encoded args differ from the args "email/onEvent" sends`. Because a component's IDs compare as strings, the host may type an ID the component sends with `Component.id`. An ID of one of the host's own tables is not a string: the host's validator accepts only IDs of that table. Internal and public references both satisfy a contract. Pass the host's generated reference: a reference typed from values alone, such as a bound component's reference or a parameter annotated `Ref.Ref`, has no codecs left to compare and is refused, as is a reference built with middleware attachments typed without their middleware.

Before it asks Convex for a handle, `Callback.create` compiles the contract's and the reference's args, returns and errors to Convex validators and compares them. Args and returns must compile to the same validators, with union members in any order. Every error the host may fail with must be one the contract declares, either the same schema or one that compiles to the same validator. Reuse the contract's error classes: a rebuilt error schema that Convex cannot compile, such as one holding a template literal, is refused. A difference fails the effect with `CallbackContractMismatch`, whose message names the side and both validators:

```text
The host function does not satisfy callback contract "email/onEvent": its args compile to {"kind":"object","fields":{"state":{"kind":"string"}}}, the contract's to {"kind":"object","fields":{"status":{"kind":"string"}}}.
```

This catches what the types cannot show, such as field names hidden behind a `Record` type. A mismatch is a wiring mistake, so most hosts let it fail the function with `Effect.orDie`. A plain Convex reference (`Ref.fromFunctionReference`) carries no codecs, so only the compile-time check applies to it. Both checks compare IDs as the application sees them, so a host that is itself a component has its own IDs compared as strings, although its deployed validator accepts only IDs of that table.

Validators do not capture everything a codec checks. Tuples with the same elements in another order compile to the same validator, a refinement such as `Schema.NonEmptyString` compiles to plain `v.string()`, a recursive schema compiles to `v.any()`, and `Schema.DateFromString` and `Schema.DurationFromString` both compile to `v.string()`. The compile-time check still compares tuples by position. Codecs that differ only in refinements, recursive structure or how they decode pass both checks.

A package that wraps its component in a client can accept the host's reference and create the handle itself. Forward the reference's type to keep the check at the caller:

```ts src/confect/client.ts
import { Callback as CallbackContract, type Ref } from "@confect/core";
import { Callback } from "@confect/server";
import * as Effect from "effect/Effect";
import { OnEvent } from "./callbacks";

export const send = <R extends Ref.Any>(args: {
  readonly to: string;
  readonly onEvent: R & CallbackContract.Check<typeof OnEvent, R>;
}) =>
  Effect.gen(function* () {
    const onEvent = yield* Callback.create<typeof OnEvent, R>(
      OnEvent,
      args.onEvent,
    );
    // ...
  });
```

### Runtime behavior

- A handle string is stable across deploys of the same code. Its format differs between `convex-test` and a real backend, so never assert it in tests.
- Creating a handle for a function that is not deployed is a defect (`Function handle not found`).
- If a host removes a function after handing it out, running the stored handle fails with the same message, and `Scheduler.runAfter` fails when it schedules rather than when the job runs.
- A call whose args the host's validator rejects reaches the component as a defect, not a typed error. That is a contract breach, not an expected failure.
- `Callback.toFuture(ref)` views a reference as Convex's `FunctionReference_future` with its wire types, for `createFunctionHandle` and clients that accept it. Workpool's `onComplete` option (0.4.14) accepts only the classic `FunctionReference` type.

## Publish the package

Build the Convex and Confect trees to JavaScript and emit their TypeScript declarations. Preserve relative imports and the generated files they reference, or bundle the corresponding entry points. A package whose output mirrors `src/` under `dist/` can expose:

```json package.json
{
  "exports": {
    "./convex.config.js": {
      "types": "./dist/convex/convex.config.d.ts",
      "default": "./dist/convex/convex.config.js"
    },
    "./_generated/component.js": {
      "types": "./dist/convex/_generated/component.d.ts"
    },
    "./confect": {
      "types": "./dist/confect/_generated/component.d.ts",
      "default": "./dist/confect/_generated/component.js"
    }
  },
  "files": ["dist"]
}
```

Export callback contracts and their errors from their own client-safe entry point (for example `./callbacks`) so a host can implement a callback without importing the component's functions. Include the runtime dependencies used by your component (`effect` and the relevant `@confect/*` packages), and declare compatible Convex requirements. The Confect contract's dependency graph must contain specs and codecs, not implementation modules. Include all transitive contract declarations as well as the deployable functions and schema in the package.

Vanilla Convex consumers install `@example/counter/convex.config.js` and call its generated component API without importing the Confect contract. They supply encoded arguments and receive encoded results; for example, `Schema.FiniteFromString` is a string on the wire. They observe declared failures as Convex errors rather than Effect failures. Confect consumers bind the additional `/confect` export to get decoding and typed errors.

Confect does not run Convex's component codegen, build your npm package, or publish it for you. Before publishing, inspect `npm pack --dry-run` and test the packed artifact from a separate consumer project using both interfaces.

## Test a component

Publish a `/testing` helper that registers the component's generated Convex schema and module loaders. Its `register` function accepts `TestConfect.RegisterComponent` and the installation path:

```ts src/testing.ts
import type { TestConfect } from "@confect/test";
import schema from "./convex/schema";

const modules = import.meta.glob("./convex/**/!(*.*.*)*.*s");

export const register = (
  registerComponent: TestConfect.RegisterComponent,
  name: string,
) => registerComponent(name, schema, modules);
```

Pass the helper through the `register` option when constructing the host's test layer:

```ts
const layer = TestConfect.layer(
  applicationSchema,
  convexSchema,
  applicationModules,
  {
    register: (registerComponent) => register(registerComponent, "counter"),
  },
);

const program = Effect.gen(function* () {
  const t = yield* TestConfect.TestConfect<typeof applicationSchema>();
  yield* t.mutation(counter.counter.create, { count: 3 });
}).pipe(Effect.provide(layer));
```

The registration path must match the installed component path. The module map follows `convex-test` conventions and includes the component's Convex `_generated` files. Register the same definition at two paths to test instance isolation. The effectful `t.registerComponent(path, schema, modules)` method remains available for registration after setup.

To fetch component HTTP routes, also list each installation's `componentPath` and `httpPrefix` in the layer's `httpMounts` option, then call `t.fetch("/counter/route")` with the full mounted path. A component kit used at multiple HTTP mounts must supply a fresh router factory in its HTTP module loader. See [mounted component HTTP tests](/guides/testing#fetch-mounted-component-routes) for setup and the process environment, module cache, and transport limits.
